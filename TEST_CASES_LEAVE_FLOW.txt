  [F] FAIL  →  Kết quả sai, ghi bug vào bảng Bug Log cuối file
  [S] SKIP  →  Bỏ qua, ghi lý do

  Cách thực hiện:
    1. Đọc "Điều kiện tiên quyết" → chuẩn bị dữ liệu và tài khoản tương ứng
    2. Làm từng bước trong "Các bước thực hiện" trên giao diện UI
    3. So sánh với "Kết quả mong đợi" → khoanh [P] hoặc [F]

└─────────────────────────────────────────────────────────────────────────────┘

Mục đích:
  Ngăn chặn Admin duyệt đơn nghỉ khi chưa giải quyết các lịch hẹn của khách bị ảnh hưởng, tránh việc khách đến tiệm mà không có thợ phục vụ.

Điều kiện tiên quyết:
  □  Đang đăng nhập tài khoản Admin
  □  Có đơn xin nghỉ bị trùng 2 lịch hẹn đặt trước của khách

Các bước thực hiện:
  1.  Vào trang quản lý phép của Admin → Tìm đơn nghỉ bị trùng lịch → Click "Xử lý trùng"
  2.  Modal xử lý hiện ra hiển thị 2 lịch trùng
  3.  Chỉ thực hiện xử lý 1 lịch (Ví dụ: click Hủy lịch khách của lịch số 1), để nguyên lịch thứ 2 ở trạng thái "Đang chờ" (pending_reschedule)
  4.  Thử click nút "Duyệt Đơn Nghỉ" ở góc dưới modal

Kết quả mong đợi:
  ✗  Nút "Duyệt Đơn Nghỉ" bị disable (không thể click)
  ✗  Nếu cố tình gọi API duyệt thẳng → Hệ thống trả về lỗi và yêu cầu xử lý hết các lịch hẹn bị ảnh hưởng trước
  ✗  Trạng thái đơn nghỉ vẫn giữ nguyên là "Chờ duyệt"

│  TC-LF-EX-04  │  Admin đổi thợ nhưng không chọn thợ mới từ dropdown         │
└─────────────────────────────────────────────────────────────────────────────┘

Mục đích:
  Đảm bảo Admin phải chọn một thợ cụ thể từ danh sách khi thực hiện hành động đổi thợ.

Điều kiện tiên quyết:
  □  Đang đăng nhập tài khoản Admin
  □  Đang mở modal "Xử lý lịch hẹn trùng" cho một đơn xin nghỉ

Các bước thực hiện:
  1.  Tại một lịch hẹn đang chờ xử lý, giữ nguyên dropdown ở trạng thái mặc định "-- Chọn thợ rảnh --" (giá trị rỗng)
  2.  Click nút "Lưu" bên cạnh dropdown đổi thợ

Kết quả mong đợi:
  ✓  Hệ thống hiển thị cảnh báo alert: "Vui lòng chọn thợ mới để đổi lịch."
  ✗  Không thực hiện gửi API đổi thợ
  ✗  Trạng thái xử lý của lịch hẹn vẫn giữ nguyên là "Đang chờ"

│  TC-LF-EX-05  │  Khách hàng truy cập trái phép vào trang Xin nghỉ / Duyệt đơn│
└─────────────────────────────────────────────────────────────────────────────┘

Mục đích:
  Kiểm tra phân quyền hệ thống (Security Test): Khách hàng thông thường không được quyền xin nghỉ của Barber hoặc duyệt đơn của Admin.

Điều kiện tiên quyết:
  □  Đang đăng nhập bằng tài khoản Khách hàng (role = customer)

Các bước thực hiện:
  1.  Đăng nhập bằng tài khoản khách hàng
  2.  Thử gõ trực tiếp URL trang xin nghỉ của Barber lên thanh địa chỉ (ví dụ: `/barber/absence` hoặc route tương ứng)
  3.  Thử gõ trực tiếp URL trang quản lý phép của Admin (ví dụ: `/admin/absences` hoặc route tương ứng)

Kết quả mong đợi:
  ✗  Hệ thống chặn truy cập, hiển thị trang lỗi 403 Forbidden HOẶC tự động redirect về trang chủ/trang lịch sử của khách hàng
  ✗  Nếu gọi API lấy lịch sử nghỉ phép hoặc duyệt đơn → Trả về HTTP 403 Forbidden hoặc 401 Unauthorized
